# 시스템 요구사항과 구성 방향

## 확정한 요구사항

한국어 엘리스 테크블로그를 주기적으로 감시하고 지식을 갱신하는 RAG QA 서비스를 만든다.
각 구성 요소를 Docker Compose 등의 방식으로 선택적으로 실행하고 연결할 수 있어야 한다.
최종적으로 엘리스클라우드에 필요한 서비스들을 배포해 QA와 평가를 데모할 수 있어야 한다.

| 구성 요소 | 책임 |
| --- | --- |
| Embedding 추론 | 문서와 질의를 같은 임베딩 계약으로 벡터화하며, 필요 시 모델을 직접 서빙 |
| Vector DB | 청크 벡터와 검색용 메타데이터 저장·조회 |
| Knowledge 서비스 | 원본 감시, 수집·정제·청킹·색인, 문서 이력·출처·지식 상태 관리 |
| RAG 시스템 | 질의 검색, 근거 기반 생성, Citation 및 근거 부족 처리. Agentic RAG 확장 고려 |
| Eval Harness | 고정한 Gold Set과 지식 버전으로 평가하고 개선 전후 결과 비교 |
| MLOps 시스템 | 평가 실행·실험 설정·지표·추적 결과 관리. Langfuse·MLflow 등은 후보 |

구성 요소는 논리적인 책임을 뜻한다. 각 책임을 반드시 별도의 애플리케이션이나 컨테이너로
나눠야 하는 것은 아니다. Knowledge와 RAG의 프로세스 경계는 구현 설계에서 결정한다.

## 선택적 실행과 연결

- 로컬에서 필요한 구성만 실행할 수 있는 인터페이스를 제공한다.
  Docker Compose를 사용한다면 profiles 또는 override 파일로 선택할 수 있도록 한다.
- 직접 실행하는 모델 서버와 외부 추론 API를 설정으로 연결할 수 있도록 설계한다.
  서버 주소·모델 식별자·인증정보는 환경별 설정으로 주입한다.
- 사용하지 않는 추론 서버나 MLOps 시스템을 불필요하게 기동하지 않는다.
  구성에 필요한 서비스가 빠졌다면 시작 또는 준비 상태 검사에서 원인을 설명한다.
- MLOps 추적 기능을 끄고도 QA를 실행할 수 있도록 한다.
- 컨테이너 내부 통신 주소와 호스트·외부 접근 주소를 구분하고, 데이터는 영속 볼륨에 저장한다.
- 임베딩 모델·차원·전처리 계약이 바뀌면 기존 인덱스와 섞어 검색하지 않도록 재색인 경계를 둔다.

## 원본 감시와 지식 관리

- `/ko` 테크블로그 목록을 주기적으로 확인해 신규·수정·삭제 후보를 찾는다.
  목록 변경만으로 기존 글의 본문 수정까지 탐지할 수 있다고 가정하지 않는다.
- 원본이 지원하는 경우 조건부 HTTP 요청을 활용하고, 본문 해시와 주기적 재검증으로
  중복 다운로드·임베딩을 줄인다. 요청 간격·재시도·실패 기록을 관리한다.
- 최종 URL과 실제 본문의 한국어 여부를 검증한다. 영어 응답이나 일시적인 수집 실패를
  기존 한국어 문서의 정상 갱신 또는 삭제로 처리하지 않는다.
- 변경된 문서만 다시 처리하고, 갱신으로 생긴 오래된 청크를 정리한다.
  갱신 실패가 기존의 정상 검색 상태를 훼손하지 않도록 한다.
- 원본 URL·섹션·게시/수정/수집 시각·본문 해시와 처리 설정을 기록한다.
  원문·문서 메타데이터·파생 벡터의 관계를 유지하고 재색인할 수 있어야 한다.
- 운영 지식 갱신과 평가용 지식 버전을 구분한다. 평가 실행 중 원본이 바뀌더라도
  비교 대상 Corpus·Gold Set·모델·프롬프트·검색 설정을 식별할 수 있도록 한다.

## 엘리스클라우드 데모 완료 기준

- 로컬에서 검증한 구성을 환경 설정을 통해 클라우드에서 재현한다.
- 필요한 API 추론 또는 GPU 서빙 자원과 영속 저장소를 연결한다.
- Ingest → 검색·Citation QA → Eval 실행과 결과 확인을 시연한다.
- 원본 변경 확인 및 증분 갱신 과정을 확인할 수 있는 실행 방법과 로그를 제공한다.
- 설치·기동·환경 변수·데이터 준비·종료 절차와 비용상 제약을 README에 기록한다.

## 아직 결정하지 않은 사항

모델, Vector DB, RAG 프레임워크와 agentic 동작 범위, MLOps 도구, 스케줄러,
서비스 분리 범위, Compose 구성 방식과 엘리스클라우드 배포 대상은 아직 확정하지 않았다.
배포 환경의 실제 지원 기능과 자원·비용을 확인한 뒤 결정한다.
위 요구사항 전체를 v0.1.0의 범위로 확정한 것은 아니며, milestone별 구현 순서는 별도로 정한다.
