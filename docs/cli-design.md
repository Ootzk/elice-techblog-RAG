# 운영 CLI 구상

이 문서는 운영 CLI의 목적과 설계 원칙을 기록한다. 현재 `tools/operations/rag`에서 환경 생성·서비스 관리·모델·Corpus·평가·보고서 진입점과 로컬 MLflow 기동을 제공한다. 실제 명령과 사용 방법은 README를 따른다.

## 목표

환경 초기화, 모델 선택, Corpus 처리, 평가와 보고서 생성의 진입점을 하나로 모은다. 운영자가 현재 상태와 다음에 필요한 작업을 확인하고 단계별로 재실행할 수 있게 한다. CLI는 기존 Knowledge·Eval Harness·보고서 기능을 호출하며 같은 로직을 별도로 구현하지 않는다.

## 명령 구성 초안

| 명령 | 책임 |
| --- | --- |
| `rag doctor` | 선택한 환경의 설정과 의존성, 준비 상태를 확인한다. |
| `rag setup` | DB, MLflow Dataset·Prompt·Judge 등 초기 설정 상태를 확인하고 필요한 등록을 수행한다. |
| `rag model` | 모델 프로필 목록·등록·선택 및 선택한 Judge의 Gateway 등록을 관리한다. |
| `rag corpus` | 수집·청킹·색인과 관련 상태를 관리한다. |
| `rag prompt` | 프롬프트 등록과 버전·alias 선택을 관리한다. |
| `rag dataset` | Gold·Iron 검증과 MLflow Dataset 등록을 관리한다. |
| `rag evaluate` | 답변 생성과 고정 답변의 모델 채점을 실행하고 결과를 조회한다. |
| `rag report` | Agreement·Repeatability·Comparison 결과와 보고서를 생성한다. |
| `rag serve` | 서비스 실행 상태와 Compose 실행 방법을 안내한다. |

`setup`은 각 기능의 진입점을 묶지만, Corpus 수집·색인과 평가까지 무조건 실행하지 않는다. Compose는 우선 기존 실행 수단으로 유지한다.

## 동작 원칙

- dev와 prod의 환경 파일과 대상 MLflow를 명시적으로 선택한다. 다른 환경이나 홈서버로 자동 전환하지 않는다.
- `doctor`는 설정과 접근 가능 여부를 확인한다. 실제 유료 추론은 기본 검사에 넣지 않고 별도 요청으로 구분한다.
- 초기화는 기존 상태를 확인해 안전하게 재실행할 수 있어야 한다. 같은 이름의 기존 리소스와 요청한 설정이 다르면 차이를 알리고 조용히 덮어쓰거나 동일하다고 간주하지 않는다. 확인할 수 없는 비밀값은 검증 불가로 표시한다.
- 실제 키는 Git에서 제외된 환경 파일에 보관하고 CLI 출력·실험 결과에 노출하지 않는다. 모델 식별자와 endpoint는 `models.json`에서 관리한다.
- 임베딩 모델이나 생성 계약 변경 시 기존 색인과 혼합하지 않는다. 모델 전환과 새 색인 준비 상태를 구분해 표시한다.
- 평가나 보고서 실행 결과에는 식별 가능한 Run ID와 출력 경로를 표시한다. 이름으로 결과를 찾는 방식은 ID의 고유성·충돌 처리를 정의한 뒤 구현한다.
- 운영 중인 리소스 삭제나 기존 설정 교체는 별도 명령으로 구분한다. 등록 명령이 사용자의 기존 설정을 자동으로 삭제하지 않는다.

## 구현 순서

1. 명령 구조와 환경·모델 설정 계약을 정한다.
2. `doctor`로 환경별 설정과 연결 상태를 확인한다.
3. 모델·Dataset·Prompt·Judge의 초기화와 기존 리소스 확인을 연결한다.
4. Corpus와 평가 명령을 통합한다.
5. 저장된 결과를 이용하는 보고서 생성 명령을 통합한다.

각 단계는 실제 구현과 검증을 마친 뒤 실행 문서에 반영한다. 새 MLflow와 이미 사용하는 MLflow를 모두 대상으로 확인한다.
